# Triage the issue queue

Read the untriaged issues, check each one's claim against the code, and label it. Comments and
labels are the entire output: this routine never closes an issue, never writes code, never opens a
pull request.

It is the model-invocable equivalent of the `mattpocock-skills` plugin's `/triage`, which carries
`disable-model-invocation: true` and so can only be typed by a human in an interactive session —
and which lives in `~/.claude/plugins/`, outside this checkout, so a cloud sandbox does not have it
at all. Same five states, same disclaimer line, same "verify before you label" spine. The
differences are deliberate and stated below.

## Reach the tracker the way this session can

`gh` is on a local machine and is **not** installed in a cloud sandbox. Establish which you are in
before spending a turn on a command that cannot run:

- **Cloud / no `gh`** — use the GitHub MCP tools, loading them in one call rather than one at a
  time:

  ```
  ToolSearch select:mcp__github__list_issues,mcp__github__issue_read,mcp__github__issue_write,mcp__github__add_issue_comment
  ```

  `Bash`/`Grep`/`Read` still work, and are how you read the checked-out repo.
- **Local** — `gh` as usual; [docs/agents/issue-tracker.md](../../../docs/agents/issue-tracker.md)
  has the exact invocations.

Either way, read [docs/agents/triage-labels.md](../../../docs/agents/triage-labels.md) first. It
maps the canonical role names the skills speak to the label strings this tracker actually uses;
where the two differ, the tracker's string is the one that goes on the issue.

## The queue

Untriaged is an issue with **no labels at all**, or one carrying `needs-triage`. Work oldest first.

**An empty queue is a complete, successful result.** Say so in one line and stop — do not go
looking for other work, do not open a pull request, do not touch the repo. The queue being empty is
the outcome, not a failure to find the task.

## One category, one state

Every triaged issue ends with exactly one of each, and `needs-triage` removed.

**Category**

- `bug` — renders or behaves wrongly, including a shipped violation of a rule this repo states.
- `enhancement` — new capability, refinement, or open question.

**State**

- `ready-for-agent` — fully specified: an agent could execute it with no further human input.
  Correct even for large work, as long as the body decides every open choice.
- `ready-for-human` — blocked on a judgment only a person can make: a product or positioning call,
  a design trade with real cost, a legal or policy question, or a genuinely open choice.
- `needs-info` — too vague to act on.

Most issues here declare which they are in a **Why it isn't already done** section. Trust it, but
override it when the **Proposed change** already resolves the doubt it raises — an author who talks
themselves out of a decision and then makes it anyway has written a `ready-for-agent` issue.

`waiting-on-external`, `parked` and `in-progress` are modifiers, not states. Leave them exactly as
they are; an issue keeps its state while it is being worked.

## Verify before you label

Read the code the issue names and confirm its claim holds. Then check **redundancy**: search for an
existing implementation by domain concept rather than by the issue's own wording, and say where you
looked. An issue asking for something the repo already does is the premise most likely to be wrong,
and wording-only searches are how it survives triage.

Report what you found, and say plainly when a premise is false. **That is the main value of this
pass** — a label is cheap and an unexamined framing is what makes a queue look longer than it is.
Never accept an issue's framing untested.

## One comment per issue

Open with this exact line, no variations:

```
> *This was generated by AI during triage.*
```

Then the outcome and the reasoning, shaped by the state:

- `ready-for-agent` — add what the body misses: the trap to avoid, the test that would catch a
  regression, where the scope stops.
- `ready-for-human` — state the decision, the options with a recommendation, and what becomes
  delegable once it is answered.
- `needs-info` — ask specific answerable questions. "Please provide more information" is not one.

## What this routine never does

**Never close an issue, apply `wontfix`, change code, or open a pull request.** If something reads
like `wontfix`, label it `ready-for-human` and explain why — closing is Aaron's call, and this is
where this skill deliberately parts company with the plugin's `/triage`, which does close and does
write a rejection to a `.out-of-scope/` knowledge base. This repo has no such directory and does
not want one: a rejected issue that stays open with the argument written on it is readable by the
next session, and a closed one is not.

Doing a follow-up's actual *work* is a different task with its own routine — that is
[backlog-routine](../backlog-routine/SKILL.md), off the `ready-for-agent` queue this pass fills.

Finish with a one-line summary of what you triaged.
