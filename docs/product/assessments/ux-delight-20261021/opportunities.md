## Six approved opportunities and their baseline rationale

## O-01 — Make account sessions recognizable before revoking a device

**Tracker:** [2861](https://github.com/AaronBuxbaum/diveday/issues/2861) · relative effort M.

**Baseline observation.** The Account security page renders the raw user-agent and IP for each
active session (page.tsx:251–273), without a current-session marker. At 390px, each synthetic Chrome
session is a multi-line technical block. The many sessions in the screenshot were generated by this
audit; the labeling problem does not depend on that artificial count.

**Approved scope.** Use a conservative browser/OS display label, a verified This device marker when
the server can identify the current session, and last-seen time as the primary row. Put raw
user-agent/IP behind details. Keep unknown-device fallbacks, all-session visibility and the existing
live authorization and revoke behavior. Do not infer precise location or a device identity from an
IP address.

**Evidence of success.** Cover known and malformed user agents, missing fields, current/other
sessions, a long list and 390px keyboard navigation. Verify revocation still affects only the
selected authorized session. Security review is required for implementation.

## O-02 — Offer a bounded continuation for additional duplicate candidates

**Tracker:** [2862](https://github.com/AaronBuxbaum/diveday/issues/2862) · relative effort M.

**Baseline observation.** MergeDiver intentionally shows the strongest five candidates, then renders
And N more as plain text (lines 56–57,91–93). Its test explicitly expects this cap. The cap protects
the record from a giant list, but gives no local way to compare candidate six.

**Approved scope.** Keep five candidates at rest and add an explicit bounded Show more or search
continuation. Preserve ranked reasons, owner/manager authorization and the existing side-by-side
comparison before any merge. Never turn this into bulk or one-tap auto-merge.

**Evidence of success.** Use at least eight candidates; reach candidate six by keyboard and pointer
without unbounded initial rendering. Confirm the comparison remains the mutation gate and live merge
safety checks still refuse conflicts.

## O-03 — Find a rental unit by tag or size inside the counter cart

**Tracker:** [2863](https://github.com/AaronBuxbaum/diveday/issues/2863) · relative effort M.

**Baseline observation.** The counter rental cart renders every unit in the selected kind as a grid
(CounterRentalCart.tsx:225). Global gear search already supports tags/serials/brands, but navigating
there does not select an item in this cart. Large-fleet friction is a hypothesis, not a measured
pilot result.

**Approved scope.** A local tag/label/size filter, visible selections across filters, unavailable
reasons and existing #2723 refusal recovery are prepared in D. A synthetic fleet of 100 tanks and
80 wetsuits was the baseline proposal for comparison, not a measured before/after result. The
original unfiltered 390px baseline was not measured; candidate counts and authored comparisons do
not establish observed task gains.

**Evidence of success.** Compare exact-tag and size lookup before and after at 390px. Verify
clearing a filter, changing kinds, blocked units and retained selections. Server availability and
pricing checks remain authoritative.

## O-04 — Show the details of a pending request to move a seat

**Tracker:** [2864](https://github.com/AaronBuxbaum/diveday/issues/2864) · relative effort M.

**Baseline observation.** MoveAsk.tsx:31–37 replaces the form with a brief acknowledgement once
asked. It does not show the request note or when it was sent. The existing staff-controlled move
request is deliberate H-20261014-ask-to-move; this is a refinement of its receipt, not self-service rescheduling.

**Approved scope.** Show the current standing request summary and time beside an explicit
waiting-for-shop state. Bind it to the current booking/departure, hide it after
move/answer/deletion, and do not reveal staff-private reply text. A request is never an accepted
move, held replacement seat or refund commitment. Defer amend/withdraw controls until their
lifecycle is designed.

**Evidence of success.** Test refresh, repeated request, staff answer, cancellation, move to another
departure and an expired or held identity. Exercise a concurrent staff move so a stale request
cannot be presented as pending for a new trip. Require dive-domain and security review.

## O-05 — Open the saved public storefront from the branding editor

**Tracker:** [2865](https://github.com/AaronBuxbaum/diveday/issues/2865) · relative effort S.

**Baseline observation.** The profile/branding editor includes a useful inline BrandPreview but its
rendered main content has no link to inspect the saved public storefront. A shop owner must navigate
elsewhere to see the actual cover, description and booking context together.

**Approved scope.** Add a restrained View public page link near the saved outcome using public route
helpers. Make clear that it shows saved settings; preserve unsaved edits and keep the live
swatch/type preview. Avoid adding a second site editor or implying unpublished changes are live.

**Evidence of success.** After saving branding, follow the link to the correct shop and confirm
rendered values. Cover unsaved edits, keyboard access, phone layout and Spanish copy.

## O-06 — Give setup requesters a safe receipt they can find later

**Tracker:** [2866](https://github.com/AaronBuxbaum/diveday/issues/2866) · relative effort M.

**Baseline observation.** After a setup request, the thank-you page acknowledges it; announce.ts
sends an operator alert, not a requester receipt. The operator alert includes a founder-only
single-use setup capability. A requester who closes the thank-you page has no durable receipt from
this path.

**Approved scope.** A separate minimal requester receipt with the submitted shop name, next step
and support route. Never reuse the operator-alert template or include its setup token. Retain
abuse/rate limits for unverified addresses, delivery observability and manual onboarding. Do not
invent a response-time promise. Existing #2834 tracks the operator alert Reply-To issue separately.

**Evidence of success.** Prove the requester template contains no capability, private operator data
or onboarding access. Test retries and duplicate submission without email flooding, undeliverable
mail, correct locale and retained request when delivery fails. Require security review before
implementation.

### Carry forward the approved Interest decision

The live issue discussion confirms the full cleanup was approved. The concept is **Interest** in
schema, code, glossary and ADR. Wait-list invitations are service mail. The discount sender belongs
under Divers → Who wants in; Details keeps deal history. The booking transaction must not read or
write interests, and nightly invite counts must ignore deal recipients. The implementation needs the
approved design document or an equivalent approved copy; the originally referenced
`/mnt/project-files/decisions/2026-10-17-lead-redesign.md` was not available in this checkout.

This report does not reopen that design or create a competing “leads” subsystem.

## Cleanup that earns its place

**Documentation drift.** The Ingrid persona still describes hard-coded USD, while current currency
formatting and booking tests cover other currencies. The roadmap's charter discussion says there is
no boat entity, while Boats and its model now exist. Reconcile the specific premises before using
those documents to prioritize; the existence of boats does not mean private charters have shipped.
These are handoff notes, not new runtime defects.

**Local navigation and retrieval.** Repair history already lives on the diver record. A repair-board
history/search door could shorten retrieval, but it is not evidence that old repairs are
inaccessible. Likewise, global gear search already works; the rental-cart idea concerns keeping
selection in context. Validate the actual task before adding another search surface.

**Existing consolidation ideas.** Refusal handling, undo, notifications, settings, skeletons,
marketing layouts and entry doors already have proposals:
[#2708](https://github.com/AaronBuxbaum/diveday/issues/2708),
[#2764](https://github.com/AaronBuxbaum/diveday/issues/2764),
[#2732](https://github.com/AaronBuxbaum/diveday/issues/2732),
[#2740](https://github.com/AaronBuxbaum/diveday/issues/2740),
[#2769](https://github.com/AaronBuxbaum/diveday/issues/2769),
[#2746](https://github.com/AaronBuxbaum/diveday/issues/2746) and
[#2712](https://github.com/AaronBuxbaum/diveday/issues/2712). Judge them by consistent user outcomes
and reduced regression risk, not reduced line count alone.

**Audit tooling.** The broad contact-sheet runner encountered navigation collisions and redirect
cascades. Fresh contexts per targeted route produced more trustworthy coverage. Future audit runs
should report expected versus actual URL, role, viewport and capture outcome per page so a
screenshot count cannot become a misleading coverage claim. This is a tooling note, not a product
navigation defect.

## Research questions before more functionality

These are observation prompts, not hidden implementation commitments or established defects.

- Does “about two minutes” on readiness/waiver entry match real completion time, including reading
  the release and medical branching? Measure with first-time participants. If unsupported, change
  the expectation, not the approved medical questionnaire.
- Can a first-time buyer find convincing product evidence and reach the working demo from the
  current marketing page? Test comprehension and task discovery before changing the hero or adding
  screenshots above every fold. Do not invent testimonials or operational claims.
- Does a returning diver lose useful work when navigating back in a multi-person public booking?
  The form uses client state, but this audit did not reproduce a loss. Any persistence proposal
  needs a privacy review and an explicit allowlist; staff draft rules do not automatically apply.
- Does Team's collection of maintenance disclosures slow common tasks with a larger crew? Trial
  a compact person summary opening existing edits, preserving role and emergency-contact access.
  The current rendering is not proven unusable.
- Can an expired-password user find the fresh reset request through sign-in without confusion?
  Existing terse recovery is deliberate; observe before adding another permanent control.
- Can a Spanish-speaking staffer complete a disrupted task, including its refusal and recovery?
  Three Spanish layouts were sampled; full translation quality and error-boundary parity remain
  unproven. Legal/medical English is an explicit decision, not missing translation work.

## What not to add on the strength of this audit

Do not reopen manual onboarding as a self-service account project. Do not re-propose prepaid
packages as memberships, gear search as missing, or postcard sharing as absent. Do not treat SMS or
WhatsApp provider approval as a front-end build gap;
[#1449](https://github.com/AaronBuxbaum/diveday/issues/1449),
[#2811](https://github.com/AaronBuxbaum/diveday/issues/2811) and
[#2812](https://github.com/AaronBuxbaum/diveday/issues/2812) already track operational dependencies.

Paid self-service rescheduling, gift cards and private charters are product scope decisions already
present in the roadmap, not urgent UX regressions established here. Preserve booking-email privacy
work in [#2691](https://github.com/AaronBuxbaum/diveday/issues/2691), and the setup-mail capability
concern in [#2834](https://github.com/AaronBuxbaum/diveday/issues/2834). A friendlier screen must
not expose private history or a founder-only setup token.
