One button on the phone that knows you; the form on every other one.

A passkey is a key the phone keeps and the phone’s own check unlocks. On a device that holds one for this account the door is a single button and a glance; a device that holds none gets the form as it ships, which is also the way back in when a phone is lost. Nothing about the door’s anatomy changes: wordmark, one question, one primary, the way out below (ADR 20260827-first-light).

What holds it in code

Better Auth’s passkey plugin, the one auth library the app already runs on, which stores the public key, the device name and the counter; a new runtime dependency and so the ADR’s. The private key never leaves the device.

The door keeps one primary. EntryShell.test.tsx already refuses a second button-shaped thing on a door; the passkey frame passes it because the password is a link.

Live revalidation is untouched. A passkey opens the same database-backed session every staff page re-reads (ADR 20260824-staff-session-live-revalidation); a disabled account is refused on its next page whichever key opened it.

Security review before merge, as any change to the door; the origin binding is the whole of a passkey’s safety and is asserted by a test against the app’s configured origin.
