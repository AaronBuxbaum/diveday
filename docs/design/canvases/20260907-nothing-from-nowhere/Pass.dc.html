What it carries, and never carries

The departure’s facts the thread’s top card shows: title, date, dock call, departure, boat, meeting place, the diver’s name, the crew-set stage. Never the thread’s URL, a booking id, a barcode, a price, a waiver or medical state, or an emergency contact. The counter checks people in by name today and keeps doing so; a pass is not a ticket.

What it needs, and why it is the owner’s (H-69 b)

An Apple Developer Program membership and a Pass Type ID certificate to sign passes; an Apple push credential so a pass can be told it changed; a Google Wallet issuer account for the Android half. Each is an account, a yearly fee and a signing secret only a human can hold, so the slice is filed waiting on that and ships nothing until it exists. The signing library is a new runtime dependency and the ADR names it.

Where it lands

One line on the thread, beside Add to calendar, on every state after booking. One pass per booking, in the shop’s brand, or DiveDay’s own tokens for a shop that set none. The pass’s update web service is two new public routes (register, fetch) that answer only to a pass’s own authentication token, which is why the security reviewer reads the slice.

What renders otherwise

The thread as it ships: Add to calendar and nothing beside it. A phone with no Wallet, a shop whose diver declined, a pass whose certificate is not yet held: the line is absent, never a broken button. Declined, this board is the one on the canvas that renders nothing at all.
